(1) Who pays: check the loss to every party, not only to the caller. If a shared pool, escrow, protocol fund or
another user pays for each repetition, replay or failed attempt, that is a loss even when the caller's own net

(2) Documented design: a candidate is accepted design only if the documentation explicitly accepts the harmful
consequence. Documentation that only describes the mechanism is not enough.
(3) Preconditions: if the default or canonical configuration avoids the precondition, do not stop there. Search
the code for every function that can write the state that the precondition needs. For each one, check who can call it and whether its inputs are
validated on-chain. Check whether a function that forwards caller-supplied calldata, payloads or configuration without
checking their content can create the precondition. If a path available to an attacker under the threat model can create the precondition, the candidate is reachable. Before you rule a
precondition unreachable, name the function or functions you checked. If another candidate in your shard
describes the enabling step, judge the combined chain as well.
(4) Limited keys: If the threat model includes compromise of a scoped or limited key or signer, treat
compromise of that key as an untrusted capability, not as trusted participation. The question is whether the key
can cause more harm than its scope is meant to allow, for example by choosing unbound arguments or by obtaining wider permissions. If any trusted role signs content that a limited-key-controlled
component builds and the on-chain code does not bind or check that content, check whether that path lets the key exceed its intended scope.
(5) Supported configurations: if the code explicitly reads and honours a flag, mode or parameter value, that
value is a supported configuration, not a misconfiguration, even when it is not the default, unless the documentation or threat model explicitly excludes that configuration. Harm that follows
when a trusted role sets a supported value as intended is in scope subject to the threat model and lowers only the likelihood. It is not a
reason to reject.
(6) External dependencies: an external protocol's routine, benign operation counts as realistic, for example a
version or patch upgrade, a parameter change or normal market activity. If that operation disables user exits,
cancellations, repayments or protective orders while user funds or open positions stay at risk, assess severity using the project's severity rubric. Do not dismiss the finding solely because another recovery path exists, for example withdrawals. Check whether that path prevents or limits the harm from the disabled operation.
