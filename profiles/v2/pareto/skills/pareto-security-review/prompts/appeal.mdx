Verifiers lose real issues in a few repeated ways. Restoring those issues is your job. You do not re-judge
candidates that are correctly rejected. Check each rejection against the patterns below.
- "Unreachable because the default or shipped configuration never sets X." Look in the code for any path that
  sets X, and look in candidates.md for another candidate that supplies it, whether that candidate is accepted
  or rejected. Count paths available under the threat model. Two flaws that
  together give a reachable loss count as reachable, even if each looked harmless alone.
- "Needs a trusted role, or the documented off-chain policy never issues this." First check whether the code
  enforces that policy. Check whether the policy is enforced on-chain or by a component whose correct behavior is assumed in the threat model. If the role only signs
  routine authorisations and an ordinary participant decides how to use them, the participant is the actor.
  Rejecting is still right when the claimed loss itself is false, for example when no party suffers the claimed loss.
- "By design" or "bounded by the user's own signed limits." Check whether a third party can choose when, or
  whether, that bounded action happens, against the user's intent. Examples are forcing a trigger by moving a
  price the attacker controls, or replaying an authorisation beyond its intended single use. A user-chosen
  bound does not make an attacker-forced execution harmless.
- "Small per-operation amount." Check whether an actor can repeat it across operations or transactions,
  including failing ones, while the action remains possible. If so, judge it by the total it allows.
