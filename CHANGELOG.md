# Changelog

## Unreleased

### Breaking changes

- **[runtime] [artifacts] [prompts] [cli] [modal] [evmbench] [docs]** The final report's Run summary gains a `Commit` line after `Repository`: `report.json` `run_metadata.target_commit` is now required, the run's 40-character lowercase hex source revision (`run.json` `source_revision`, the commit every task worktree is created from) or `null` when the run recorded none, rendered as ``- Commit: `none` (no Git commit was recorded for the evaluated target)``. `report.md` no longer renders `Source run ID`, `## Scoped coverage evidence` or `## Artifact validation warnings`: `report.json` keeps `source_run_id`, `source_run_ids`, `coverage_evidence` and `run_metadata.artifact_validation_warnings`, the public bundle now requires both `artifact-validation-warnings.json` and `artifact-validation-warnings.md` whenever the report carries warnings, a fixed sentence after the Run summary says when scoped coverage could not be measured or was measured but incomplete, and the final-report gate now rejects a scoped coverage section or exact-scope coverage score in `report.md` with `REPORT_COVERAGE_EVIDENCE_MARKDOWN_UNEXPECTED` instead of requiring the section (`REPORT_COVERAGE_EVIDENCE_MARKDOWN_MISSING`). Every production issue now ends with `### Remediation`, showing the selected source finding's `recommendation` or a fixed sentence saying that no remediation was recorded; the report stage only carries `recommendation`, so a production issue row that adds, changes or omits one fails verification (a non-production row that changes or omits one gets a warning, and one that adds one fails), and `ultrafuzz/findings@2` producers are asked to set it only when their cited evidence establishes the fix. Backtick spans in finding prose (titles, descriptions, rationales, Proof of Concept steps, family variants and remediation) now render as inline code, and the public projection also redacts a private path written right after a literal `\`, `>`, `&lt;`, a word-starting `|`, or a run such as `/*` or `/<`, and a home, private-directory, drive-letter or UNC path also right after `;` or `*`, so text that now renders more literally cannot reveal one. `Estimated spend` is now the USD amount of accounting v4 (`accounting.cumulative.estimated_spend_usd`), the figure `ultrafuzz stats`, eval accounting and Modal worker results read, never `unavailable` (`$0.00` when nothing was priced), and followed by `+` when the amount is probably low; `run_metadata.estimated_spend` must match `^\$(?:0|[1-9][0-9]*)\.[0-9]{2,10}\+?$`. Usage that was never recorded or could not be priced is not estimated: the spend ends in `+` exactly when `run_metadata.partial_pricing` is true or the new optional `run_metadata.attempts_without_usage` or `run_metadata.unpriced_attempts` count is present, and the report schema rejects a `+` that disagrees with them. `report.md` renders neither count, and an empty model list renders as ``- Models used: `none` (no model usage was recorded)``. `run.json` gains an `attempts_without_usage` member that lists the executed agent attempts with no usage event of their own, with a `cumulative_count` that includes source runs. Accounting v4 now prices a packaged default model that the pricing catalog leaves unpriced, whether the catalog is available, unavailable or disabled, at the versioned list prices `ultrafuzz.fallback-pricing.2026-10-05`, copied from models.dev on that date, and records them in `pricing_catalog.model_prices` and the new `pricing_catalog.fallback`; those models stay in `unresolved_models` but now count as priced in `ultrafuzz stats`, eval accounting and Modal worker results, which also accept an `available` pricing catalog that reports unresolved models instead of failing validation. v4 also looks up a model it has not already priced through a route-exclusive catalog lookup: one leading `openrouter/` is stripped, an ID containing `/` or starting with `~` is priced only from OpenRouter, `claude-`, `gpt-`, `chatgpt-`, `o<digit>`, DeepSeek and Kimi or Moonshot IDs only from their first-party entries and any other ID not at all, a trailing `[...]` context alias is stripped, and a catalog entry with zero input and output rates is ignored unless the ID ends in `:free`; a model that v4 used to price from whichever aggregator sorted first can therefore stay unpriced. Runtime presentations restate models, tokens, spend, `partial_pricing` and the counts from run accounting, keep the agent's copy without it, and set the `+` again from the restated fields; `ultrafuzz report` diagnostics accept `$0.00` and expect the `+` whenever `run.json` says the amount is probably low. Because `ultrafuzz/report@3` and `run.json` change in place, reports written before this release no longer verify, and no longer render as unchecked reports either, since they fail the schema, and a controller from an earlier release rejects a `run.json` that this release has synchronized; finish a run launched on an earlier release with that release. EVMbench grades the copied `report.md` as `audit.md`, so its scores are not comparable across this release. Projects scaffolded earlier keep their old `.ultrafuzz/prompts/review/final-report.md`; delete it and rerun `ultrafuzz init` to pick up the new prompt (#1268).
- **[runtime] [artifacts] [modal] [docs]** Removes campaign data governance (#1269). Where campaign data goes is a trust assumption about the inference providers you configure, and Ultrafuzz never enforced it: agents run unsandboxed, so the policy, acknowledgements and route IDs recorded intent without stopping any data. Review each provider's data-handling terms yourself, as [Inference provider data handling](docs/security.md#inference-provider-data-handling) describes. `ULTRAFUZZ_DATA_GOVERNANCE_POLICY` and `ULTRAFUZZ_DATA_DISCLOSURE_ACKNOWLEDGEMENTS` are no longer read, and campaigns have no `private` or `public` mode. A target with uncommitted changes, such as the files `ultrafuzz init` scaffolds (#1226), no longer fails `DATA_GOVERNANCE_PRIVATE_TARGET_UNBOUND`. No `DATA_GOVERNANCE_*` or `DATA_DISCLOSURE_*` diagnostic remains, and the Claude, Codex, DeepSeek, Kimi and OpenRouter adapters no longer fail with "provider route changed after disclosure acknowledgement". Runs no longer write `data-governance.json`, and `plan.json` moves to `ultrafuzz.run-plan.v4`, which drops `data_governance`. `json validate` no longer recognizes the `data-governance-policy` and `data-disclosure-acknowledgements` schemas. `ultrafuzz-modal` launches and oversees private standalone benchmarks again instead of refusing them pending R-26. Rerun `ultrafuzz init` to refresh `.smithers/agents/`; until then planning fails with `CONTROLLER_SOURCE_UNTRUSTED`. A run planned by an earlier release has an `ultrafuzz.run-plan.v3` plan, which every command that reads the run's sealed workflow, such as `status`, `why`, `events`, `node`, `timeline`, `snapshots`, `pause`, `cancel`, `resume`, `replay` and `fork`, refuses with an unsupported-version diagnostic, so finish or cancel runs before upgrading; `inspect` and `ps` still show such a run. `clean` removes nothing from a selection that includes such a run (`CLEAN_SOURCE_REF_FAILED`). Delete it by hand with `chmod -R u+w .ultrafuzz/runs/<id> && rm -rf .ultrafuzz/runs/<id>` and `git update-ref -d refs/ultrafuzz/runs/<id>/source`. First check its `plan.json` for an `execution.mode` of `cloud`, because `clean` can no longer read that plan to report `CLEAN_CLOUD_STORAGE_RETAINED`.
- **[runtime] [docs]** Without `ULTRAFUZZ_PROVIDER_HOME_ROOT`, the provider-home root is now `~/.ultrafuzz-provider-homes`, which the adapters create with mode `0700`, instead of `$XDG_STATE_HOME/ultrafuzz/provider-homes` (by default `~/.local/state/ultrafuzz/provider-homes`), and `XDG_STATE_HOME` no longer moves it. That root holds the homes of `OpenRouterAgent`, `DeepSeekAgent`, and a `ClaudeAgent`, `CodexAgent` or `KimiAgent` with a `config_dir`. Ubuntu's default umask `0002` makes `~/.local` `0775`, and the provider-home check, which still refuses a group- or world-writable directory above a provider home unless it is sticky, refused the old root there, so those agents could not start (#1236). Nothing is read from or moved out of the old root. `OpenRouterAgent` and `DeepSeekAgent` use API keys and keep no login in their homes, so they only start without their earlier session history. A `ClaudeAgent`, `CodexAgent` or `KimiAgent` with a `config_dir` finds its home empty: with `auth = "subscription"` it is not logged in, and a provider config file kept in the old home, such as a Codex `config.toml` that selects a route, no longer applies. To keep that state, move the old root into place before an agent first runs on this release: `mv "${XDG_STATE_HOME:-$HOME/.local/state}/ultrafuzz/provider-homes" ~/.ultrafuzz-provider-homes`. To log in again instead, first create the home with `(umask 077; mkdir -p ~/.ultrafuzz-provider-homes/<provider>/<config_dir>)`, where `<provider>` is `claude`, `codex` or `kimi`, then log the CLI in with that directory as `CLAUDE_CONFIG_DIR`, `CODEX_HOME` or `KIMI_CODE_HOME`. Codex refuses a home that does not exist, and a plain `mkdir -p` under umask `0002` would make the directories it creates `0775`, which the check refuses, as in #1236. If you set `XDG_STATE_HOME` to keep these homes elsewhere, set `ULTRAFUZZ_PROVIDER_HOME_ROOT` instead. That variable also moves the home of a `ClaudeAgent`, `CodexAgent` or `KimiAgent` without a `config_dir`, from `~/.claude`, `~/.codex` or `~/.kimi-code` (or `CLAUDE_CONFIG_DIR`, `CODEX_HOME` or `KIMI_CODE_HOME`) to `<root>/claude`, `<root>/codex` or `<root>/kimi`. Rerun `ultrafuzz init` to refresh `.smithers/agents/provider-home.ts`. A run launched earlier runs the adapters sealed at its launch, and so keeps the old root, until `resume --refresh-controller`.
- **[config] [runtime] [prompts] [docs]** A property lens that fails no longer stops the campaign. The packaged `default` topology, which `ultrafuzz init` scaffolds, and the packaged `exhaustive` and `invariant-only` topologies change: their `properties` group now has `failure_policy: continue`, and `property-specification-fanin` moves to a new `property-catalog` group, which still halts. The fan-in consolidates the lenses that passed verification, and the strategies, specialists and review run without the failed lens's properties. The report is PARTIAL when the lens ran out of attempts and unverified when it failed its output contract, unless a later `resume --retry-failed` reruns the lens successfully. That resume, which Modal's durable resume always runs, reruns the failed lens, and when the lens's artifact verifier failed, also every node that started after the lens's attempt, which is most of the campaign. In `exhaustive`, `dynamic-strategy-generator` now also runs when some strategy attempts failed, using the ones that succeeded, instead of being skipped. The fan-in, strategies and specialists now have optional inputs, so when the artifact verifier of one of them fails, `state.json` no longer records `output_contracts.missing` or `terminal_disposition: task-output-validation-failure` for it and public eval diagnostics omit its `failure_code`; the verifier's error stays in `last_error`, as it already did for review tasks. The `exhaustive` and `invariant-only` profiles use the new topology after the upgrade. The `default` and `low-cost` profiles run the project's own `.ultrafuzz/topology.yml`, so an existing project keeps the old behaviour there, where one failed lens fails the run before any strategy starts and leaves it without a report, until you make three edits to that file: add `defaults: {failure_policy: continue}` to the `properties` group; add a `property-catalog` group with no `failure_policy` (the scaffold gives it `label: Property catalog` and `color: "#854d0e"`); and change the `property-specification-fanin` node's `group` from `properties` to `property-catalog`. If you have not customized that file, `ultrafuzz topology copy default .ultrafuzz/topology.yml --force` replaces it with the new default instead. Every existing project, whichever profile it runs, should also delete `.ultrafuzz/prompts/properties/property-specification-fanin.md` and rerun `ultrafuzz init`: a project prompt overrides the built-in one under every profile, and only the new prompt tells the fan-in to consolidate the lenses it is given instead of every lens in the topology.
- **[runtime] [docs]** A `failure_policy: continue` group's results are now optional to every node outside that group, including nodes with no `group` and the nodes a dynamic group generates, not only to the group named `review`. Such a node runs without a failed input instead of being skipped, while nodes in the same group still require it. A node that reaches a failed ancestor of its own group only through another group, such as strategy `s2` after specialist `x` after strategy `s1`, now fails its input admission instead of being skipped; that is an `artifact-contract` failure, so the run's report is published unverified. To keep a chain strict, put all of it in one group.
- **[runtime] [docs]** A final-report producer retry or verifier that runs in a restarted controller (resume, quota park, supervisor relaunch) now rebuilds `report.json#run_metadata.agent_execution` from `smithers/final-report-selections/<attempt-id>.json` in the run directory, which each producer attempt writes just before starting its agent, instead of running `smithers node` as a subprocess (a `--full-output` read of up to 64 MiB under a 180 s budget). This applies to workflows rendered by this release, at launch or by `resume --refresh-controller`; plain `resume` keeps running the workflow persisted at launch, even after a refresh. So a run launched by an earlier release and continued by plain `resume` still runs `smithers node` in a restarted controller, which finds a runner only on the operator's own `PATH`, as before; continue such a run with `resume --refresh-controller`. On a run launched by an earlier release, a verifier refreshed after its producer succeeded under the old workflow fails with `report producer selection was never recorded`, and mixing plain and refreshed resumes can make it fail with `run_metadata.agent_execution differs from the controller-observed producer`; in either case run `ultrafuzz resume <run-id> --refresh-controller --reset-node <report node>` (`node:final-report` in the packaged topologies), which reruns the report producer and its verifier rather than every failed task. Producer attempts after such a refresh leave the earlier release's attempts out of `agent_execution.failed_attempts`. After a restart the verifier compares against a run-directory file instead of the Smithers database. The reference docs now say that neither is a boundary against an agent running unsandboxed as the same user, which retires #585's claim that the run filesystem cannot be used to forge the producer (Refs #1143).
- **[config] [runtime] [modal] [docs]** Removes per-node cloud execution (#134), which never completed a node in any release (#712, #713). `validate`, `doctor`, `run` and `eval run` reject `[execution] mode = "cloud"`, `execution.provider` and `[execution.providers.modal]` with `CONFIG_EXECUTION_CLOUD_REMOVED` before a run directory exists; remove `execution.provider` and `[execution.providers.modal]`, and set `mode = "local"` or delete it. The rest of `[execution]` is still accepted and validated but no longer affects execution: every agentic attempt runs locally. To use Modal, run the whole campaign inside one sandbox, as the unchanged `ultrafuzz-modal` eval runner does. A run planned with `mode = "cloud"` cannot be continued: `resume`, with or without `--refresh-controller`, reads the mode from the run's `smithers/resolved-config.json` and fails with `WORKFLOW_CLOUD_EXECUTION_REMOVED` before starting Smithers, so start a new run. It also fails, with `WORKFLOW_LIFECYCLE_FAILED`, for a run whose resolved config is missing or does not parse, which a plain `resume` used to continue without it. `ultrafuzz clean` no longer terminates Modal sandboxes tagged `purpose=ultrafuzz-node` or deletes the `ultrafuzz-node-*` volumes of earlier cloud attempts; remove those by hand in the Modal app the run used, which its `plan.json` records under `execution.providers.modal` until `ultrafuzz clean` deletes the run. The runtime `cloud-execution-generation` schema and the seven Modal node schemas are deleted, so `json validate` no longer recognizes them.
- **[runtime] [docs]** Prompts are no longer sealed or compared after launch. A run's `artifacts/<attempt>/prompt.rendered.md` is the prompt that attempt receives on every verb (launch, `resume` with or without `--refresh-controller`, `--retry-failed` or `--reset-node`, `replay` and `fork`); a runtime prompt is rendered only while its file is missing and is otherwise used as it is, without the validator-command check, which now runs only on fresh renders. Editing that file, or a template copy under `dynamic-prompt-templates/` before its prompt is rendered, changes what the task's next attempt receives, unless a later `resume` first renders the project's prompt over it, which `[run] refresh_prompts_on_resume = false` turns off, and no longer strands the run or stops `status` from synchronizing. This replaces the upgrade note for #1176 and #1195: a run launched by an earlier release whose published prompts this release renders differently no longer fails with `runtime rendered prompt changed`, so it can be synchronized, resumed and reported again. A prompt that cannot be rendered, or a prompt file that is missing, unreadable or not a regular file (a symlink or a directory), now fails only its task at `assert-task-inputs` with the cause, instead of stopping every render; fix the file and `resume --retry-failed`. The verifier that runs after the agent no longer checks the prompt, so an edit or deletion after the agent started cannot fail its finished work. Admission no longer opens runtime prompts, so it reports neither a missing one nor one that is not a regular file, and no longer checks the vulnerability-database catalog digest, which is checked only when a prompt is rendered. New runs' execution snapshots no longer contain `controls/rendered-prompts/` or `controls/prompt-snapshots/`; `prompt-snapshots/` is only the copy that `resume`, `replay` and `fork` restore a missing static prompt from, before they start an engine and without a digest check, and nothing at a prompt path, not even a dangling symlink, is ever replaced. `resume --retry-failed` of a dynamic source now records its withdrawal of the published generation in `dynamic-expansion-history/.retry-withdrawal.json` from before its first step until after its last, and moves the generation's attempt state before its manifests: a withdrawal interrupted before its manifests move leaves the published generation in place instead of a withdrawn prompt beside a new manifest, and the next `resume` completes an interrupted withdrawal, whichever step it stopped at, before it starts an engine. `replay` and `fork` complete it too, except one that stopped after its manifests moved and before the task plan was re-derived: `replay`, `fork` and synchronization refuse that run until a `resume` has completed it. These errors are gone: `runtime rendered prompt changed for …`, `runtime rendered prompt is missing for …`, `DYNAMIC_TEMPLATE_CHANGED`, `persisted prompt plan does not match continuation task …`, `retained rendered prompt snapshot digest does not match task …`, `continuation prompt binding is missing for …`, `persisted prompt plan does not match compiled task …`, `retained rendered prompt snapshot does not match task …` and `sealed rendered prompt is missing for …`. What is given up: a process running as the operator, including an agent in another task, can change a later task's prompt or template copy undetected, and `replay` and `fork` use the current prompt files instead of the launch bytes. For a run launched before this release, edit prompts only while it is paused: until it is resumed, its original engine still reads sealed copies (a static edit is lost) and still compares runtime prompts (a runtime edit stops it), and its `replay` and `fork` keep that behaviour. Continue such a run with `resume --refresh-controller` to have prompt problems fail only their task: a plain `resume` runs its launch workflow, which still stops the whole run when a runtime prompt no longer renders. For runs launched after this change, the dashboard again shows static tasks' rendered prompts, because the launch engine no longer deletes them; it shows each file as it is now, which is what the task's next attempt receives.
- **[runtime] [config] [prompts] [cli] [docs]** `resume` now applies the project's current prompts to the tasks of a run that have not finished, by default. Every `resume`, with or without `--refresh-controller`, `--retry-failed` or `--reset-node`, does so after the checks that can refuse it and before it resets anything or starts the engine. It selects each prompt exactly as `run` does, from `.ultrafuzz/prompts/**` and the packaged built-ins, renders it the way the run's launch did, with the run's own config, and rewrites what the tasks whose agent the workflow engine does not report `finished` will receive: the prompts of static tasks, including those a reset reruns and the tasks that depend on them, the rendered prompts of generated children and of nodes that waited on a dynamic group, such as the final report, and the template copies under `dynamic-prompt-templates/` that a later render reads, those of groups that have not expanded and of tasks whose prompt is not rendered yet. A finished task keeps its `prompt.rendered.md`, and when `--retry-failed` reruns a dynamic source, the withdrawn generation's prompts move to `dynamic-expansion-history/` as they ran, while the group's template copies take the edits. Before it changes a file, the refresh writes `prompt-history/<time>-<id>/refresh.json`, which lists every file it rewrites with its old and new SHA-256; it then copies each file beside it and replaces it atomically, and resume reports `PROMPTS_REFRESHED`. The refresh never fails a resume. A prompt that `run` would reject, that does not render for one of its tasks, that names an artifact authority one of its static tasks was not compiled with, or that shares a template copy a later render reads with a prompt whose new text differs keeps every file rendered from it and is reported as `PROMPT_REFRESH_REJECTED`, while the other prompts still apply. `PROMPT_REFRESH_SKIPPED` means it applied nothing because the effective topology file differs from the one the run launched with (any edit, even to a comment), a prompt file breaks the whole catalog as it would break `run`, such as invalid frontmatter or a duplicate `id`, `ultrafuzz.toml` cannot be read, or the engine still reports the run active. Such a catalog error now names its file, for `run` and `validate` too, and a duplicate `id` names both files. `PROMPT_REFRESH_INCOMPLETE` means it stopped part way and says how many files it replaced; each file `refresh.json` lists holds either its old or its new bytes. What changes for you: a hand edit of an unfinished task's `prompt.rendered.md` or of a template copy is replaced by the next `resume` (its bytes stay in `prompt-history/`); to keep such edits, set the new `[run] refresh_prompts_on_resume = false`. `resume` reads that key from the project's current `ultrafuzz.toml`, not from the run's configuration frozen at launch, so it also applies to runs already in flight, and it appears in neither `config.resolved.toml` nor `smithers/resolved-config.json`. An edit to `.ultrafuzz/prompts/**`, or an upgrade that changes a packaged prompt, now reaches a run in flight at its next `resume`, not only new runs. A `resume` of a run the engine still reports active only attaches and applies nothing, so pause the run and resume it once `status` reports it paused. `prompt_digest` and the run's other prompt digests keep their launch values, and `refresh.json` is the only record of a refresh. A reset also reruns finished tasks that merely started after the reset task, which keep their prompt, and when the engine then fails to reset a task, the resume fails with that task's file already rewritten. For a run launched by an earlier release, resume with `--refresh-controller`: its launch workflow stops the whole run, instead of one task, when a prompt rendered from a rewritten template copy no longer renders. Its `replay` and `fork`, which run its launch snapshot, stop at their first render once a resume has rewritten one of its runtime prompts or template copies; set `refresh_prompts_on_resume = false` before you resume such a run that you still need to replay or fork.
- **[runtime] [artifacts] [docs]** A run keeps validating its artifacts against the schemas it was planned with, and an upgrade that changes a schema, even by one `$comment`, no longer fails every resumed task. Each artifact's contract validation by the workflow's verifier and dependency admission, and by synchronization's findings count, now uses the run's planned schema bundle, as the host artifact gates already did (#1188): this build's schemas when their bundle digest is the planned one, otherwise the copy sealed in the run's execution snapshot. Task preparation copies that bundle into the task's `.ultrafuzz/schemas`, replacing a copy that differs instead of failing on it, and runs the validator preflight only for a task with a schema-backed output, requiring the run's own validator to report the planned bundle instead of this build's. These failures are gone for runs launched with this change: `prompt schema destination differs from checked-in source` at `materialize-prompt-schemas`, `planned schema binding changed for …` at `assert-task-output-schema-bindings`, a step that no longer exists, and `JSON validator preflight returned an invalid success envelope` (`mismatched identity`) at `preflight-json-validator`, also for a plan with no schema-backed output; neither `--retry-failed` nor `--refresh-controller` recovered them. `resume --refresh-controller` no longer rebinds declared outputs to the installed bundle (#982): the refreshed workflow keeps each output's recorded schema binding, so its verification markers keep matching the plan, and after a schema change the refresh keeps the run's own validator launcher without trying the installed CLI, which validates with other schemas, and without a `WORKFLOW_TRUSTED_CLI_UNVERIFIED` warning. Validations against a sealed bundle, each of which starts a worker that compiles the whole bundle, now have 30 s instead of 5 s, in the workflow and on the host (synchronization's artifact gates and findings count, and verified reads), and an engine does not validate again an artifact that the bundle accepted. This build's schemas still apply where an already validated artifact is parsed into this build's types, and to the final report's canonical projection, which this build derives: the verifier's properties JSON/Markdown parity, invariant-suite and property-coverage checks, and the workflow's and host's semantic contexts that read properties, implemented-properties, property-campaign and campaign findings artifacts. An upgrade that tightens one of those schemas within the same contract version can therefore still fail a resumed task, after its agent ran when the task produces that artifact. What is given up: a run no longer adopts an upgrade's schema fixes, so start a new run to use them; and a task's `.ultrafuzz/schemas` copy is no longer tamper-evident, because preparation rewrites a copy that differs without refusing or recording it (the run's own validator still rejects a schema file whose bytes are not the planned ones, and after a schema change the engine reads the planned bundle from the run's execution snapshot). `parseJsonValidatorPreflightSuccessEnvelope` now requires the expected identity and no longer defaults to this build's findings binding, and `materializePromptSchemas` takes the bundle to copy and drops `replaceExisting`. Continue a run launched before this change with `ultrafuzz resume <run-id> --refresh-controller`, every time: its launch workflow still calls `materializePromptSchemas` the old way, which this release rejects in every task, and a plain `resume` runs that workflow even after a refresh, so it now fails with `WORKFLOW_CONTROLLER_REFRESH_REQUIRED` before Smithers starts. This replaces #1230's note that a plain `resume` runs such a run's launch workflow. An engine that the supervisor relaunches from an install upgraded in place, which the CLI reference already advises against, fails each task at `materialize-prompt-schemas` with `this run's workflow was rendered by an earlier Ultrafuzz release …`; continue it with `resume --refresh-controller --retry-failed`, which reruns a failed verifier from its agent.
