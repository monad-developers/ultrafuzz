Separating provider, harness, and model

A re-analysis of issue #653 after "DeepSeek Code" was corrected to mean deepseek-ai/deepseek-harness. DeepSeek Harness is a real, first-party, MIT-licensed harness — and it is a developer preview whose only supported CLI output is prose. This report records what was measured, which pairings to adopt, what to build, and in what order.

1 · Verdict

Keep Codex for OpenAI, adopt Pi as the OpenRouter default, and add DeepSeek Harness as the first-party pairing for DeepSeek V4 only, scoped to nodes that need a final artifact rather than a live event stream. Do not make DeepSeek Harness a generic OpenRouter harness, and do not rename the existing DeepSeekAgent onto it — that adapter is Claude Code against DeepSeek's Anthropic-compatible endpoint and should be renamed to say so.

Why this shape

The three choices in a model profile — gateway, harness, catalogue ID — have different release cadences and different failure modes. A first-party harness tracks its own vendor's wire dialect and reasoning controls without translation, so it is the right default whenever the operator has already chosen that vendor. A gateway has no harness of its own, so it needs one designed for arbitrary provider routes. Everything else is a compatibility path that stays supported and stays non-default.

2 · The correction and what it invalidates

The previous draft concluded that no first-party DeepSeek coding CLI existed in the deepseek-ai organization and that no CLI should be blessed under the name "DeepSeek Code". That conclusion is withdrawn. Three claims in that draft were wrong or incomplete, and all three are now corrected in provider-harness-research.md.

4 · Recommended pairing policy

First-party is the default

OpenAI → Codex CLI. Anthropic → Claude Code. DeepSeek V4 → DeepSeek Harness (dsh), final-text-only and only once it is qualified. A vendor's own harness tracks its own wire dialect, reasoning levels, and cache semantics without a translation layer.

Gateways get neutral harnesses

OpenRouter is a gateway with no harness of its own, so it defaults to a provider-neutral one: Pi first, OpenCode second. Both accept an opaque catalogue model ID and emit machine-readable events.

Compatibility stays legal

Codex + OpenRouter and Claude Code + DeepSeek keep working with a documented migration path. They are supported combinations, never the recommended shape for a new project.

Evidence promotes, claims do not

A pairing becomes default only after a pinned real CLI clears every gate in §8 against the real provider. Kimi already ships; any further first-party pairing earns its place the same way.

The one pairing to decline

DeepSeek Harness as a general OpenRouter harness. It can reach OpenRouter through its pi-ai route, but it deliberately sends no OpenRouter attribution headers, exposes no structured stream, and vendors the very provider layer Pi ships — so choosing it for OpenRouter costs observability and buys nothing.

5.1 · The final-text-only event class

DeepSeek Harness forces a new capability value. Rather than block the whole integration on an upstream feature we cannot file an issue for, the contract admits a harness whose only output is a final answer plus an exit code — and the validator refuses to schedule it onto a node that needs per-tool events or token accounting. 

events: "jsonl" | "rpc" | "final-text-only"

// Node declares what it needs; the validator does the matching.
node.requires = { events: "jsonl" }   // dashboard/telemetry node → dsh rejected
node.requires = { events: "final-text-only" } // artifact node → dsh allowed

The ceiling is lower than it looks, and that is deliberate. dsh's session log is readable typed JSONL once decompressed, but Ultrafuzz does not read it: the format is undocumented and "version":0 on a prerelease that promises breaking changes, against an upstream that accepts neither issues nor pull requests. There is no session parser in this plan. The capability value stays final-text-only, and the evidence a dsh node does produce comes from a small real-dsh smoke profile that lives inside the adapter issue (#653-D) — headless final text plus exit status, one filesystem/shell artifact check in a disposable worktree, a version pin asserted at preflight, and an explicit final-text-only fallback that warns rather than failing the run.

5.2 · Credential and state rules that survive every harness

  • The child environment is built from an empty or tightly allowlisted base, never inherited wholesale.
  • Exactly one provider credential is present, and it matches the endpoint the harness will call.
  • Credentials never appear in argv — this rules out Smithers' PiAgent --api-key path.
  • Every harness gets a run-scoped state root, so no run reads or writes an operator's real home.
  • The invocation cwd must not carry harness-readable config. For dsh this means proving no .env exists in the target worktree before launch — both because an unset name there would be adopted, and because a bootstrap-only name there aborts the harness.
  • The state root does not live inside a region the harness's own sandbox leaves writable. dsh's workspace-write policy grants all of /tmp under the Landlock runner, so a DSH_HOME under /tmp is reachable by the agent's own shell — put it beside the worktree instead.
  • Assume the child shell sees harness-injected environment. dsh strips ambient DSH_* but then supplies DSH_HOME, DSH_SHELL, DSH_SESSION_ID, and DSH_SESSION_JSONL; the credential scrub (/KEY|PASSWORD|SECRET|TOKEN/i) is what keeps the provider key out, not the DSH_* handling.

6 · Sequencing

  1. Phase 0 — schema and validator, no behavior change

    Land [providers]/[harnesses]/[models] plus the binding validator with legacy agent = "…" profiles mapped forward. Default selection is untouched, so this is reviewable in isolation.

  2. Phase 1 — Pi + OpenRouter to qualification

    The first non-Codex OpenRouter harness. Requires an OPENROUTER_API_KEY in CI or a maintainer environment; blocked on credentials, not on design.

  3. Phase 2 — DeepSeek naming first, then the DeepSeek Harness adapter

    Rename the legacy binding to Claude Code + DeepSeek (pure terminology, no runtime change), then add the dsh adapter behind harness = "dsh", restricted to final-text-only nodes, with a small real-dsh smoke profile rather than a session-log parser.

  4. Phase 3 — OpenCode as the second OpenRouter option

    Only after Pi proves the wrapper pattern for state isolation and disabled update/share surfaces.

  5. Phase 4 — Modal image capability gate

    Prove sandbox runners and pre-baked state roots in the pinned worker image for every approved harness. Nothing becomes a default until it passes here.

  6. Phase 5 — default decision

    Choose the OpenRouter default from comparable real-provider results. Until then Codex remains the shipped default by inertia, and that is stated rather than implied.

7 · Risks

Risk Severity Mitigation
dsh breaking changes between prereleases high Pin the exact version, assert dsh --version at preflight, and keep the adapter's surface to --profile headless plus environment. Upstream says breaking changes will happen.
No upstream issue or PR channel for dsh high Treat dsh as an unpatchable dependency: no workaround may depend on an upstream fix. Keep Claude Code + DeepSeek as the fallback pairing for the same provider.
Prose-only output blocks dashboards and cost accounting high Constrain dsh to final-text-only nodes and enforce it in the validator. Accept the loss rather than parsing the undocumented version: 0 session log; the #653-D smoke profile keeps the adapter honest with final text, exit status, and one artifact check. Revisit only if the ACP server ships in the CLI or a JSON mode becomes supported.
Target-repo .env configures — or aborts — the harness medium Preflight assertion that the invocation cwd holds no .env, or launch from a clean directory with the workspace passed explicitly. Downgraded from high after reading loadLayeredEnv: inherited values always win, so a repo .env cannot override the credential Ultrafuzz supplies. The sharper failure is the other direction — an ordinary developer .env carrying HTTP_PROXY, NODE_OPTIONS, DEEPSEEK_BASE_URL, or any DSH_* name makes dsh exit with a bootstrap-name error before the agent starts. Preflight must produce that diagnostic itself rather than surface it as an opaque harness crash.
workspace-write leaves all of /tmp writable high Measured, not inferred: under the Landlock runner the grant list is /dev/null, /tmp, and the workspace root, and a write to /tmp outside the workspace succeeded. The bwrap runner instead gets a private --tmpfs /tmp, so two machines with the same policy string enforce different boundaries. Keep no run-scoped secret material, DSH_HOME, or sibling worktree under a shared /tmp when the Landlock rung is the one that wins; assert the selected runner at preflight and treat /tmp as agent-writable in the threat model regardless.
Sandbox unavailable in the Modal image low Image capability check in Phase 4. SANDBOX_UNAVAILABLE fails closed, so this surfaces as a total shell-tool outage rather than a silent downgrade — detect it at build time. Downgraded after measurement: in this unprivileged container bwrap could not map uids and the Landlock rung carried the whole suite, which is the configuration a Modal worker most resembles. The residual risk is packaging, not the kernel — the Landlock launcher ships as optional per-arch dependencies (linux-x64, linux-arm64), so an image built with --no-optional or on an unlisted arch loses the last rung.
Hidden second provider call per session (title generation) medium Account for it in cost models, or disable the session-title-llm row through the profile patch layer in the run-scoped DSH_HOME. Mitigation verified: a --patch overlay setting {id: session-title-llm, disabled: true} took a real run from two provider requests to one, with identical stdout and exit 0.
Anonymous identity header reaches configured gateways medium Route through dsh-llm-pi-ai rather than deepseek-official when the endpoint is not DeepSeek's own, and document that DSH_TELEMETRY_DISABLED does not suppress it.
Smithers PiAgent puts the API key in argv medium Leave the adapter's apiKey option unset and supply the credential only through childEnv; add a conformance test that inspects the spawned argv.
No paid credentials in the research environment medium Every qualification issue below is explicitly blocked on a credential. Local-endpoint evidence is labelled as such and never counted as provider qualification.
Four harnesses to maintain low The capability contract is the containment: harness-specific behavior lives behind it, and an unmaintained harness can be dropped by deleting one binding.
