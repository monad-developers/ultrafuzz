R-01

Do not grant execution authority to target-supplied .smithers code

HighConfidence: MediumScope: L

Affected surface

packages/runtime/src/init.ts · agent-registry.ts · validate.ts · smithers.ts (installed-runner validation, adapter sealing) · templates/smithers/workflows/workflow.tsx registry import

Rationale

Non---force initialization preserves a pre-existing project-local .smithers tree. Registry validation checks only that factory names exist and adapters pass a narrow substring check; installed-runner validation checks version, bin metadata and file layout but never compares executable bytes against registry integrity metadata or a trusted release digest, and the compatibility patcher returns successfully when all expected packages are absent. The generated workflow then imports that registry in controller context. A target repository that ships a correctly-shaped .smithers therefore executes as the operator before any model, prompt, or artifact gate runs. This is distinct from YOLO: it is controller-plane code provenance, not agent permission mode. Notably, neither threat-model baseline enumerated this as a threat — it surfaced only in the code-level skills — so it is a gap in both threat models as well as in the code.

Proposed change

Install the runner into an operator-controlled cache or sealed per-run directory from a lockfile carrying registry integrity hashes; authenticate the complete execution closure and an exact adapter file allowlist against packaged digests before import; fail closed on pre-existing target-owned executable .smithers files; require a non-persisted, digest-recorded operator approval for any genuinely custom adapter.

Anthropic claude-fable-5 — not raised

Threat / countermeasure mapping

No mapping in either baseline. Adjacent to OA-T1 (prompt-driven host compromise) but the reports do not assert that link; treat as an unmodelled threat that should be added on the next threat-model refresh.

R-02

Universal secret gate on canonical agent artifacts before publication

HighConfidence: HighScope: M

Affected surface

packages/runtime/src/verified-output.ts · materialize.ts · run-documents.ts · generated workflow finalizeAndVerifyArtifacts / publishVerifiedArtifacts · packages/security/src/sensitive-redaction.ts call sites

Rationale

Both families independently reached the same conclusion from different directions: redaction is a logging/eventing control, not an artifact control. Events, diagnostics, final-report projections and Modal public bundles are redacted; report.md, findings.json and generated tests are schema-validated and then persisted byte-for-byte with no secret scan. Because the same bytes are handed to downstream agents and can be materialized, a credential an agent copies into a free-form finding, evidence or note field survives every existing gate. Anthropic additionally notes the domain-specific case that matters most for a smart-contract tool: a raw blockchain private key or seed phrase.

Proposed change

Scan every agent-controlled output and companion file before canonical publication, using both maintained patterns and the run's exact known secret values. Reject contaminated artifacts by default; where raw evidence must be retained, keep a restricted raw copy and publish a redacted derivative with a manifest linking the transformation. Fail closed, matching the existing public-bundle behaviour.

R-03

Operator-owned credential-name and provider-home policy

HighConfidence: MediumScope: M

Affected surface

packages/config/src/agents.ts (api_key_env, config_dir schemas) · packages/runtime/src/start-run.ts environment-name collection · generated adapter requiredEnv helpers · templates/smithers/agents/openrouter.tsx provider-home materialization

Rationale

Repository-controlled TOML picks which host environment variable is read as the provider credential — validated only as an environment-variable-shaped name against a small controller-only denylist — and which directory becomes the provider home, validated only as non-empty. An affected profile can therefore send an unrelated host secret to a provider as authentication, or cause the OpenRouter adapter to create/replace config.toml at an absolute path outside the project. This is a data→configuration→credential crossing that exists independently of YOLO: it is decided before any agent starts, so no agent-level control would mitigate it.

Proposed change

Move credential names and provider roots into operator-owned policy: canonical per-adapter credential names by default, any exception requiring a separate exact-name acknowledgement from outside the repository; restrict generated provider homes to a dedicated Ultrafuzz state root, rejecting absolute and symlink-crossing paths by default, with exceptions bound to an approval that displays the resolved path and provider origin.

R-05

Expand redaction patterns, add an entropy fallback, thread exact secret values

MediumConfidence: HighScope: S–M

Affected surface

packages/security/src/sensitive-redaction.ts (SECRET_PATTERNS, isSensitiveSecretValue, redactSecretsInValue) and all at-rest call sites in artifacts/src/{events,state}.ts, runtime/src/workflow-sync.ts

Rationale

The pattern set is an allowlist of known shapes with no high-entropy fallback, and the same redactor is the fail-closed "contains secret" gate on public disclosure surfaces — so an unrecognized secret both survives redaction and passes publication. A non-destructive probe replicating the exact patterns confirmed these are not redacted: Google AIza… keys; web3 RPC URLs with the key in the path (eth-mainnet.g.alchemy.com/v2/<KEY>, mainnet.infura.io/v3/<KEY>) — directly relevant since MAINNET_RPC_URL is a documented opt-in agent variable; bare npm_… tokens; Modal ak-/as- tokens; and generic 40-hex secrets. R-06

Stop returning the dashboard session token from an unauthenticated route

MediumConfidence: HighScope: M

Affected surface

packages/dashboard/src/index.ts — session(), handle() API gating, requireLocalRequest(), requireMutation(), the command dispatcher, and the token-free read/SSE routes

Rationale

Both families agree on the mechanism and disagree sharply on impact — worth recording rather than averaging. GET /api/session returns the mutation credential to any caller passing only the loopback Host/Origin/sec-fetch-site checks, which authenticate the request context, not the caller; all read endpoints and SSE streams require no token at all. Holding it authorizes config, topology and prompt writes plus run / resume / replay / fork / references-update / materialize / clean. OpenAI rates this High, arguing loopback TCP does not distinguish OS users so another local user gains full authority. Anthropic rates it Low/Informational, arguing a same-UID process could already invoke the CLI directly. Both are right within their assumption: the delta is real and material only on shared or multi-user hosts. Reconciled to Medium; the fix is cheap relative to the disagreement.

Proposed change

Deliver the credential out of band — e.g. a dashboard URL carrying the token in its fragment, consumed and stripped by the frontend — and require it on every API route including reads and SSE. The session response must never contain the token. Rotate it periodically or give it a short lifetime with silent loopback refresh. Where the platform supports it, prefer an owner-only Unix-domain socket or peer-credential check over loopback TCP; otherwise use a 0600 per-user token handshake.

R-07

Per-child provider-credential scoping in multi-provider local runs

MediumConfidence: HighScope: S

Affected surface

packages/runtime/src/start-run.ts (agentEnvironmentVariableNames) · smithers.ts forwarded set · templates/smithers/agents/environment.tsx (workflowControlChildEnvironment)

Rationale

In a multi-provider topology every active api-key agent's credential is collected into the single controller environment that every spawned agent child inherits. The per-child sanitizer blanks only controller-internal SMITHERS_/ULTRAFUZZ_ variables — not sibling provider keys. Apply per-invocation credential scoping in workflowControlChildEnvironment so each agent child receives only its own provider's key and every non-active provider key name is blanked, mirroring the existing cloud and OpenRouter behaviour.

R-13

Short-TTL token exchange and per-row credential volumes on Modal

MediumConfidence: MediumScope: M

Affected surface

packages/modal/src/auth.ts (subscriptionAuthCopy, shared-volume staging of the Kimi refresh token) · packages/modal/src/runner.ts (stageSubscriptionAuthEntry) · packages/modal/src/layout.ts

Rationale

Long-lived subscription OAuth credentials — the Claude credentials file and the Kimi OAuth material including the refresh token — are staged as files into cloud sandboxes that execute model output, and the Kimi refresh token is deliberately placed in a volume shared across campaign rows. A refresh token mints new access tokens indefinitely, and cross-row sharing means any single run in a campaign can read a token usable well outside its own row. The right framing under the YOLO constraint: the agent's ability to read whatever is in its environment is accepted; what is not forced by that acceptance is the credential's lifetime and lateral reach. Shortening both is a compensating control, not a permission change.

Proposed change

Exchange the refresh token for a short-TTL access token on the controller and forward only that; scope credential volumes per row rather than sharing them across a campaign; keep operator-dispatch-only staging; record the residual explicitly in docs/security.md alongside the existing trust-model statement.

Why these two scores must not be averaged

A mean of 33.8 and 28.4 would be 31.1 — a number with no threat model behind it. ARI is normalized against its own model's risk capacity, so two scores are only comparable when they share a threat set, an asset inventory and a severity calibration. These do not:

  • Different denominators. Risk Capacity is 49 in one model and 28 in the other — a 1.75× difference driven by different threat counts and severity weightings. The same absolute residual risk produces a different ARI in each. Averaging normalized ratios with different normalizers is not a defined operation.
  • Different threat sets. Eleven threats versus ten, enumerated independently. The OpenAI model separates configuration-driven credential abuse (T2) and private evaluation disclosure (T10) as distinct High threats; the Anthropic model does not enumerate them. The Anthropic model separates CI fork-PR secret exposure (T10) and public publication integrity (T8); the OpenAI model folds these into supply-chain and evidence threats.
  • Colliding IDs, different meanings. The identifiers are not a shared namespace. OA-T3 is provider/cloud disclosure; CL-T3 is secret leakage via artifacts. OA-T4 is secret persistence; CL-T4 is target-code confidentiality to third parties. Cross-mapping by number produces wrong conclusions. Every mapping in this document is namespaced OA- or CL- for that reason.
  • Different asset inventories and severity calibration. Thirteen assets versus eight, including two intangible assets (user trust, contractual standing) present only in the Anthropic model. The same mechanism can therefore land at different severities — target-code confidentiality is High in one model and Medium in the other — which is a genuine analytical difference, not noise to be smoothed.
  • Different grade gates fire. One is capped at D by four High threats with gaps ≥ 0.50; the other is capped at C by exactly one. The caps are not commensurable, and no arithmetic on the two numbers reproduces either gate.

Use them as two independent readings. Their agreement is the signal worth acting on: both concentrate residual risk in the same three places — unsandboxed credentialed agent execution, incomplete secret handling, and third-party data governance. Their disagreements (the dashboard token, semantic-signoff, dependency advisories, the ZIP parser) are documented per-recommendation above rather than resolved by arithmetic.
